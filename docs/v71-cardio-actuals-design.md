# v71 · Phase 3-2 설계안: 유산소 실측·강도 구간 기록

**상태(2026-11-17): PO 확인 4건 확정. 1단계(순수 계산기)·2단계(스키마 v7·저장·outbox)·3단계(세션 화면 입력)를 구현했다. 3단계는 JVM 테스트만 통과했고 에뮬레이터 CI·화면 캡처 확인 전이다. 상세 표시·정정 UI·워치는 아직 없다. CI·에뮬레이터·실기기 미검증.** 근거: Notion "ROUTIVE v2 · 2026-11-17 Figma 정리·정책 9건·QA/플로우 이관 기록" §8(P-08 확정 기준·사례 A~E·AC-P08-01~06), 기존 `docs/v60`~`v63`, 현재 코드.

## 1. 요구 (정책 원문 요약)
- 실제 기구 수치를 **선택 입력**한다. 입력 사건(원본)과 사후 정정은 구분해 보존한다. 미기록 구간의 수치는 **추정하지 않는다**.
- 강도별 **시작·종료 경과시간**을 남긴다. **일시정지 시간은 제외**한다(운동 경과시간 기준).
- 종료 후 실제 기록을 수정할 수 있다. **정정 전·후 값과 수정 시각**을 보존하고, 저장 실패 시 원본을 유지하며 재시도할 수 있다.
- 기록 상세에서 실제 강도 구간을 본다. 조회·저장 실패는 "미기록"이나 0과 구분한다.
- 사례(확정): A 시작부터 입력(3→5→7, 각 5분) / B 첫 입력이 늦음(앞 5분은 **미기록**, 소급 적용 금지) / C 입력 중 취소(변경 없음) / D 일시정지(제외) / E 사후 정정(원본 입력 불변).

## 3. 설계 원칙
1. **원본 입력 사건은 추가만**(덮어쓰기·삭제 없음). 구간은 입력 사건에서 **계산**한다(저장하지 않아 불일치가 생기지 않는다).
2. 시각은 **세션 활성 경과 초**로 저장한다(일시정지 자동 제외, 벽시계와 분리).
3. 첫 입력 이전과 입력이 없는 구간은 **미기록**으로 남긴다. 목표 강도·직전 값으로 채우지 않는다.
4. 정정은 기존 `session_adjustments`에 **새 행 추가**(원본 입력 사건 불변).
5. 칼로리·강도·시간을 만들어 내지 않는다.

## 4. 데이터 모델 제안 (Room v7, 추가만)
```
session_cardio_inputs
  sessionId TEXT, inputIndex INTEGER, metricKey TEXT   (PK: 한 입력 사건에 항목 여러 개 = 행 여러 개)
  stageIndex INTEGER                            유산소 ①/②
  atActiveSeconds INTEGER                       세션 활성 경과(일시정지 제외)
  equipmentKey TEXT                             Equipment 키(예: INDOOR_CYCLE)
  valueText TEXT, unit TEXT                     사용자가 입력한 그대로(숫자)
  enteredAtEpochMs INTEGER                      입력 시각(감사용)
```
- 마이그레이션은 `CREATE TABLE IF NOT EXISTS` 한 개뿐이다. **기존 테이블은 건드리지 않고** 기존 기록은 불변이다. `exportSchema` 7.json 추가, `RoutiveMigrationTest` 패턴으로 v6→v7 테스트, `verify-data-safety.py`(DROP·RENAME 금지, 스키마·마이그레이션 사슬) 통과 필수.
- 정정 필드: `cardio:<inputIndex>:<metricKey|at>`. `CorrectionField`에 파서만 확장(스키마 변경 없음).
- outbox/`TimerSnapshot` JSON에 `cardioInputs` 배열을 **버전 필드와 함께** 추가한다. 필드가 없는 구버전 항목은 "입력 없음"으로 읽는다(호환 테스트 필수).

## 5. 기록 흐름
1. 유산소 단계에서 "강도 입력"을 누르면 기구 수치 선택/입력 시트가 열린다. **저장을 눌렀을 때만** 입력 사건이 생기고, 취소는 아무것도 만들지 않는다(사례 C).
2. 구간 = 입력 사건 ~ 다음 입력 사건(또는 해당 유산소 단계 종료). 첫 입력 이전은 미기록(사례 B).
3. 종료 시 입력 사건은 기존 세션 커밋과 **같은 트랜잭션**으로 저장한다(실패 시 outbox에 남아 재시도, 중복 없음).
4. 기록 상세: "실제 강도 구간" 목록(기구 수치·지속시간·미기록 표시)과 수정 시트. 조회 실패는 오류+재시도, 입력이 없는 세션은 "수치 미기록".
5. 수정: 값만 정정하면(시각은 수정 불가) `session_adjustments`에 이전·새 값·시각이 추가되고 원본 입력은 그대로다. 저장 실패 시 기존 유효 기록 유지, Draft·재시도(근력 정정과 같은 방식).

## 10. 2단계 구현 결과 (스키마 v7, 코드 기준)
- `session_cardio_inputs`(PK `sessionId, inputIndex, metricKey`, `sessions` FK CASCADE). `MIGRATION_6_7`은 `CREATE TABLE IF NOT EXISTS` 한 문장뿐이고 `schemas/7.json`을 추가했다. 기존 테이블은 변경 없음.
- 저장은 세션 커밋과 **같은 트랜잭션**이다. 검증 실패(미지의 항목·숫자 아님·음수·세션 종료 이후 시각·중복 키·다른 세션 id)는 번들 전체를 거부해 아무것도 저장하지 않는다.
- 60초 미만·세트 없음 세션은 기존대로 저장하지 않으므로 그 안의 입력도 저장되지 않는다(PO 확정 4).
- 멱등: 같은 입력 재시도는 `AlreadyCommitted`. 저장된 값과 다른 값은 `Conflict`(저장분 불변). 한쪽에 입력이 없으면 동의로 보고 저장분을 바꾸지 않는다(plan·segments와 같은 규칙).
- outbox JSON은 `cardioV:1` + `cardio` 배열을 추가한다. 키가 없는 구버전 항목은 "입력 없음"으로 읽는다. 읽을 수 없는 입력 하나만 버리고 세션 항목은 유지한다.
- 아직 없는 것: 입력을 만들어 내는 화면(3단계), 상세 표시(4단계), 정정(5단계). 지금은 입력이 만들어지지 않아 실제 기록에는 변화가 없다.

## 11. 3단계 구현 결과 (세션 화면 입력, 코드 기준)
- 위치: 4단계 세션 화면(`RoutiveSessionScreen`)의 **유산소 단계** 운동 카드. 기존 컨트롤은 건드리지 않고 카드에 "기구 수치 입력" 버튼과 저장된 값 목록만 추가했다.
- 기구 인식: 유산소 단계 운동 이름 `실내 사이클`(→ `INDOOR_CYCLE`, 레벨) · `일립티컬`(→ `ELLIPTICAL`, 레벨+경사). 그 외 이름의 운동에는 버튼이 없다(이름으로만 판단하므로 새 유산소 기구가 생기면 `CardioMetrics`에 추가해야 함).
- 입력창은 그 기구가 가진 항목만 묻는다. **저장을 눌렀을 때만** 기록이 생기고(취소·창 닫기는 아무것도 만들지 않음), 값은 0 이상의 숫자만 받는다. 비워 둔 항목은 기록하지 않는다(이전 값을 이어 쓰지 않음). 아무 값도 없으면 저장되지 않고 안내만 보인다.
- **시각 기준(설계 §4와 다른 점):** `atStageSeconds`는 세션 전체가 아니라 **그 유산소 단계의 활성 시간**(일시정지·휴식 제외)이다. 이전 단계로 돌아갔다 와도 순서가 꼬이지 않게 하기 위함이며, 4단계(상세 표시)의 구간 계산도 이 기준(단계 창 `[0, 단계 활성 시간]`)으로 한다. DB 열 이름은 그대로 `atActiveSeconds`.
- 저장 위치: 세션 저장소(`RoutiveSession.cardioInputs`, JSON `cardioV:1`)에 즉시 디스크 반영 → 종료 시 `snapshot()`이 `TimerSnapshot.cardioInputs`로 넘기고 2단계의 같은 트랜잭션 저장 경로로 들어간다. 구버전 세션(키 없음)은 입력 없음으로 읽는다.
- 같은 단계에서 사이클과 일립티컬을 번갈아 쓰면 입력이 섞여 보일 수 있다. 상세 표시(4단계)에서 기구별로 나눠 구간을 계산해야 한다.
- 워치 입력은 없다(PO 확정: 폰에서만).

## 12. 4단계 구현 결과 (기록 상세 표시, 읽기 전용, 코드 기준)
- 상태: **구현 완료 · 미검증.** JVM 테스트(`CardioStageRecordsTest`)를 작성했지만 이 작업 환경에서 Gradle이 의존성 jar를 받지 못해(프록시가 Gradle 요청의 jar를 404 처리) **실행하지 못했다**. 컴파일·단위 테스트·에뮬레이터 캡처 모두 CI 또는 로컬 확인이 필요하다.
- 읽기 모델: `CardioStageRecords.build`가 `session_cardio_inputs`(해당 유산소 단계)와 `session_adjustments`의 `cardio:<inputIndex>:<metricKey>` 행을 읽어 `CardioIntervals.effective` → `compute`로 구간을 계산한다. 창은 `[0, 유산소 단계 실제 시간]`(§11 시각 기준). 아무것도 저장·수정하지 않는다.
- 정정 필드 규칙은 §4와 같은 `cardio:<inputIndex>:<metricKey>`로 확정(`CorrectionField.cardio/parseCardio`). 근력 필드 `set:…`와 접두어로 구분된다. 정정을 **쓰는** 코드는 5단계다.
- 화면: 기록 상세 유산소 단계 카드(기본 접힘)에 "실제 강도 구간" 목록 — `시작–종료 / 레벨 N(· 경사 M) / 지속시간`, 입력 전 구간은 `미기록`. 정정 표시·이력 없음. 저장된 값이 없는 세션은 기존 "수치 미기록"을 그대로 보인다. 한 단계에서 두 기구를 썼으면 행에 기구 이름을 붙인다.
- 접힘 기본값은 유산소 단계에만 적용했다. 준비운동·근력·마무리의 기본 펼침은 기존 테스트(`ComposeRecordTest`)가 전제하므로, 전체 단계 접힘은 별도 변경으로 결정이 필요하다.
- 아직 없는 것: "수치 수정" 진입 행·수정 시트(5단계), 조회 실패 시 오류+재시도 구분(AC-P08-06 중 유산소 부분은 현재 단계 전체 로드 실패와 같은 처리).
